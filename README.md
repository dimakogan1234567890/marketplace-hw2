# Marketplace: OpenAPI + CRUD

API маркетплейса на Python: каталог товаров, заказы с резервированием остатков, промокоды, JWT-аутентификация и роли. Контракт OpenAPI используется для генерации моделей и HTTP-обработчиков. Данные хранятся в PostgreSQL, схема создаётся миграциями Flyway.

## Требования и режимы запуска

Все команды ниже предназначены для **Windows CMD**. Каждая строка блока выполняется отдельно; следующий этап начинается после успешного завершения предыдущего. Переменные, заданные через `set`, действуют в текущем окне CMD и запускаемых из него процессах.

В примерах проект расположен в `%USERPROFILE%\Downloads\marketplace`. Для другой папки необходимо изменить команду `cd /d`.

| Режим | API | PostgreSQL и Flyway | Требования на компьютере |
| --- | --- | --- | --- |
| Локальный API | Python в `.venv` | Docker Compose | Python 3.12, Java 21 или новее, Docker Desktop с Linux containers и Compose v2 |
| Весь сервис в Docker | Контейнер `api` | Docker Compose | Docker Desktop с Linux containers и Compose v2 |

Первый запуск требует доступа к PyPI, Maven Central и реестрам Docker. В режиме Docker Python и Java для сборки находятся внутри образов. Для запуска `scripts/demo.py` и локальных тестов нужен Python на компьютере.

Прямые зависимости закреплены в `requirements.txt` и `requirements-dev.txt`: FastAPI 0.115.12, Pydantic 2.11.7, Psycopg 3.2.9, PyJWT 2.10.1, bcrypt 4.3.0, Uvicorn 0.34.3, simplejson 3.20.1, httpx 0.28.1, pytest 8.4.1. Основная версия Python — **3.12**; этот набор зависимостей не предназначен для Python 3.14. PostgreSQL — 17.6, Flyway — 11.7.2, OpenAPI Generator — 7.14.0.

## Локальный запуск API

### 1. Рабочая папка и Docker

```cmd
cd /d "%USERPROFILE%\Downloads\marketplace"
start "" "%ProgramFiles%\Docker\Docker\Docker Desktop.exe"
```

После готовности движка Docker:

```cmd
docker version
docker compose version
```

В выводе `docker version` должны присутствовать разделы Client и Server. При нестандартном пути установки Docker Desktop запускается через его ярлык.

### 2. Python, зависимости и генерация API

Проверка интерпретатора и Java:

```cmd
py -3.12 --version
java -version
```

Если Python 3.12 отсутствует, его необходимо установить. При использовании Python Install Manager доступна команда:

```cmd
py install 3.12
```

Создание окружения, установка зависимостей и генерация:

```cmd
py -3.12 -m venv .venv
.venv\Scripts\python.exe --version
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe scripts\build.py
```

Проверка окружения должна показывать `Python 3.12.x`. Уже созданное окружение другой версии необходимо заменить по инструкции в разделе диагностики. Активация `.venv` не требуется: команды используют её интерпретатор явно.

После генерации существует каталог `build\generated\src\openapi_server`. Java используется генератором; сам API выполняется на Python.

### 3. PostgreSQL и миграция

```cmd
docker compose up -d --wait --wait-timeout 120 db
docker compose run --rm migrate
```

Первая команда дожидается готовности PostgreSQL. Вторая применяет миграцию `V1__schema.sql` к базе `marketplace`; повторное выполнение не применяет уже выполненную миграцию заново. Успех отражается в выводе Flyway: миграция применена либо схема уже актуальна.

Отдельные установки PostgreSQL, `psql` и Flyway CLI на компьютере для этой последовательности не нужны. Внутри Compose база доступна как `db:5432`, с компьютера — как `127.0.0.1:5432`.

### 4. Сервер

В том же окне CMD:

```cmd
set "PYTHONPATH=.;build\generated\src"
set "DATABASE_URL=postgresql://market:market@127.0.0.1:5432/marketplace"
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8080 --no-access-log
```

Ожидается `Application startup complete`. Окно остаётся занятым сервером. При запуске создаётся пользователь `admin`, если такого имени ещё нет, поэтому доступная база с применённой миграцией требуется уже на этапе старта.

Если контейнер `api` ранее занимал порт 8080, перед локальным запуском остановить его:

```cmd
docker compose stop api
```

## Проверка API и базы

Команды выполняются во **втором окне CMD**, пока сервер работает в первом:

```cmd
cd /d "%USERPROFILE%\Downloads\marketplace"
curl.exe -i http://127.0.0.1:8080/health
```

Ожидается `200 OK` и `{"status":"ok"}`. Этот endpoint проверяет доступность HTTP-приложения и не выполняет отдельный запрос к БД.

| Адрес | Назначение |
| --- | --- |
| `http://127.0.0.1:8080/health` | Проверка доступности приложения |
| `http://127.0.0.1:8080/docs` | Swagger UI |
| `http://127.0.0.1:8080/openapi.json` | Исходный контракт OpenAPI |

HTTP-сценарий регистрации, заказа, пересчёта и отмены:

```cmd
set "API_URL=http://127.0.0.1:8080"
.venv\Scripts\python.exe scripts\demo.py
```

Сценарий создаёт уникальные учётные записи, товар и промокод при каждом запуске. Вариант без `.venv`, например после запуска API целиком в Docker: `py -3.12 scripts\demo.py`. Дополнительные библиотеки сценарию не требуются.

| Этап | Ожидаемый результат |
| --- | --- |
| Заказ трёх единиц товара по 100 со скидкой 10% | `total_amount = 270` |
| Уменьшение количества до одной единицы при минимуме промокода 200 | `total_amount = 100`, промокод снят |
| Отмена | Статус `CANCELED`, остаток товара снова 10 |

Скрипт печатает фактические и ожидаемые значения. Полные автоматические проверки выполняются через pytest.

Проверка сохранённых данных и истории миграций:

```cmd
docker compose exec -T db psql -U market -d marketplace -v ON_ERROR_STOP=1 < scripts\inspect.sql
```

Запросы выводят товары, заказы, позиции, квоты промокодов, историю операций и `flyway_schema_history`. После нескольких запусков сценария в базе будет несколько наборов данных; их идентификаторы печатаются в выводе `demo.py`.

## Запуск целиком в Docker

Это альтернативный режим. Перед его запуском локальный Uvicorn на порту 8080 останавливается через `Ctrl+C` в окне сервера.

После запуска Docker Desktop, из корня проекта:

```cmd
docker compose up --build --wait --wait-timeout 180
docker compose ps -a
curl.exe -i http://127.0.0.1:8080/health
```

Сборка генерирует API автоматически. Порядок старта: `db` проходит health-check → `migrate` применяет Flyway и завершается с кодом 0 → запускается `api`. Завершённый с кодом 0 контейнер `migrate` — ожидаемое состояние. После завершения запуска `db` и `api` должны быть healthy.

Журналы:

```cmd
docker compose logs --tail 100 db migrate api
```

Конечный образ API содержит Python и запускается от пользователя `marketplace`. Java используется только на стадии сборки; миграции выполняются отдельным контейнером Flyway.

## Автоматические тесты

Требуются зависимости из `requirements-dev.txt` и сгенерированный API: для подготовки выполняется шаг 2 локального запуска. Все команды ниже выполняются в отдельном окне CMD из корня проекта.

### Подготовка тестовой базы

```cmd
docker compose up -d --wait --wait-timeout 120 db
docker compose exec db createdb -U market marketplace_test
docker compose run --rm -e "FLYWAY_URL=jdbc:postgresql://db:5432/marketplace_test" migrate
```

База создаётся один раз. Если `createdb` сообщает, что `marketplace_test` уже существует, создание пропускается; миграция выполняется для существующей базы. Другие ошибки создания базы не следует игнорировать.

### Запуск

```cmd
set "TEST_DATABASE_URL=postgresql://market:market@127.0.0.1:5432/marketplace_test"
set "ADMIN_PASSWORD=Admin-demo-password-123"
.venv\Scripts\python.exe -m pytest -v
```

Ожидаемый итог текущего набора — **20 passed**. При последующих запусках достаточно работающей базы с миграциями и команд этого блока. Переменные необходимо задать заново в новом окне CMD.

Тесты сами запускают Uvicorn на свободном порту; сервер на 8080 можно оставить работающим. `pytest.ini` добавляет пути импорта, поэтому отдельно задавать PYTHONPATH для pytest не требуется. Тестовая конфигурация устанавливает интервал CREATE/UPDATE в одну минуту и ожидает указанный пароль тестового администратора.

**Перед каждым сценарием таблицы тестовой базы очищаются.** `TEST_DATABASE_URL` должен указывать на отдельную базу, имя которой оканчивается на `_test`. База `marketplace` не предназначена для этого запуска. Одновременный запуск двух экземпляров pytest против одной тестовой базы не поддерживается.

Проверяются:

- CRUD, пагинация и фильтры, права на товары, мягкое удаление;
- валидация полей, UUID, enum, денежных значений, JSON и обязательного тела;
- резервирование остатков, сохранение цены позиции, отмена и откат транзакций;
- пересчёт скидки, срок и квота промокода, возврат использования;
- отдельные ограничения частоты CREATE/UPDATE и переходы статусов;
- роли, владение заказом, тип и срок JWT, ротация refresh;
- JSON-журналы, `X-Request-Id` и маскирование паролей;
- конкурентные запросы к последней единице товара, последней квоте промокода, одному заказу и refresh-токену;
- применение Flyway, индекс статуса товаров и автоматические даты.

Проверки используют настоящие HTTP-запросы и PostgreSQL. Успешное прохождение подтверждает эти сценарии, но не заменяет независимую проверку требований и не доказывает отсутствие ошибок вне покрытия.

## Остановка и повторный запуск

Локальный API останавливается через `Ctrl+C` в его окне. Остановка контейнеров:

```cmd
docker compose down
```

Именованный том `pgdata` сохраняется вместе с базами `marketplace` и `marketplace_test`. Повторный локальный запуск: запуск Docker Desktop, шаги 3 и 4 раздела «Локальный запуск API». Создавать `.venv`, заново устанавливать зависимости и генерировать API при каждом старте не требуется.

После изменения `requirements*.txt` повторяется установка зависимостей; после изменения контракта, шаблонов или генератора — кодогенерация. При изменении схемы создаётся следующая миграция Flyway, уже применённая `V1__schema.sql` не редактируется. Для контейнерного API после изменения исходников повторяется сборка `docker compose up --build --wait --wait-timeout 180`.

## Структура и архитектура

```text
app/                       Рукописная реализация API
  main.py                  Создание FastAPI, подключение маршрутов, старт администратора
  handlers.py              Связь сгенерированных маршрутов с бизнес-функциями
  products.py              Каталог товаров
  orders.py                Резервы, заказы, отмена и статусы
  promos.py                Промокоды и расчёт скидки
  auth.py                  Пароли, роли, access/refresh и ротация токенов
  db.py                    Соединения, транзакции и SQL-помощники
  errors.py                Единый формат ошибок и проверки прав
  http.py                  JSON, middleware, ошибки и журналирование
  contract_types.py        Проверки скалярных типов для сгенерированных DTO
openapi/marketplace.json    Единственный исходный контракт API
templates/                 Шаблоны OpenAPI Generator
db/migration/              Версионированные миграции Flyway
scripts/build.py           Воспроизводимая генерация API
scripts/demo.py            HTTP-сценарий заказа
scripts/inspect.sql        SELECT для проверки данных
tests/                     Подготовка окружения и тестовые сценарии
requirements*.txt          Зависимости приложения и тестов
pytest.ini                 Настройки pytest
Dockerfile                 Сборка и образ API
compose.yml                PostgreSQL, Flyway и API
.gitignore                 Исключения Git
.dockerignore              Исключения контекста сборки Docker
```

Каталоги `.venv`, `.tools`, `build` и кеши создаются локально и исключены из Git. Пустой `app/__init__.py` обозначает Python-пакет.

Приложение объединяет четыре области: доступ, товары, заказы и промокоды. Единая PostgreSQL позволяет одной транзакцией изменять заказ, остатки и квоту промокода. Разделение этих операций между отдельными сервисами потребовало бы координации распределённых изменений.

Путь запроса: middleware с request_id и JWT → сгенерированный маршрут → проверка Pydantic → бизнес-функция → SQL через Psycopg → PostgreSQL. Личность передаётся через `request.state.actor`. Синхронные HTTP-обработчики выполняются в пуле потоков.

## Контракт и кодогенерация

`openapi/marketplace.json` содержит 14 операций и 22 схемы OpenAPI 3.0.3. DTO вручную не создаются. Команда генерации:

```cmd
.venv\Scripts\python.exe scripts\build.py
```

Скрипт использует OpenAPI Generator 7.14.0 с генератором `python-fastapi`. При загрузке JAR проверяется закреплённая SHA-256; файл сохраняется в `.tools`. Из исходной спецификации создаётся промежуточный `build/generator-input.json` с настройками генератора. Исходный контракт не изменяется.

Шаблоны `api.mustache` и `model_generic.mustache` и обработка результата в `build.py` обеспечивают Decimal, UUID, даты с часовым поясом, обязательные тела, ограничения полей и правильные статусы ответов. `app/contract_types.py` содержит скалярные валидаторы, а не ручные DTO.

Результат находится в `build/generated/src/openapi_server`. `main.py` импортирует сгенерированные маршруты, которые используют сгенерированные модели и вызывают `app/handlers.py`. При повторной генерации каталог `build/generated` заменяется целиком. Swagger UI получает исходный контракт через `/openapi.json`.

## API и права доступа

Все товарные операции, заказы и промокоды требуют заголовок `Authorization: Bearer <access_token>`. Для регистрации разрешены роли USER и SELLER. ADMIN создаётся при старте приложения.

| Метод и путь | Результат | Доступ |
| --- | --- | --- |
| `POST /auth/register` | 201, пользователь | Без access-токена; USER или SELLER |
| `POST /auth/login` | 200, access и refresh | Без access-токена; логин и пароль |
| `POST /auth/refresh` | 200, новая пара токенов | Без access-токена; действующий refresh |
| `GET /products` | 200, страница товаров | USER, SELLER, ADMIN |
| `GET /products/{id}` | 200, товар | USER, SELLER, ADMIN |
| `POST /products` | 201, товар | SELLER, ADMIN; seller_id берётся из текущей личности |
| `PUT /products/{id}` | 200, товар | SELLER — свои, ADMIN — любые |
| `DELETE /products/{id}` | 204, пустое тело | SELLER — свои, ADMIN — любые |
| `POST /orders` | 201, заказ | USER, ADMIN; заказ текущего пользователя |
| `GET /orders/{id}` | 200, заказ | USER — свои, ADMIN — любые |
| `PUT /orders/{id}` | 200, заказ | USER — свои, ADMIN — любые; только CREATED |
| `POST /orders/{id}/cancel` | 200, заказ | USER — свои, ADMIN — любые; до оплаты |
| `POST /orders/{id}/status` | 200, заказ | Только ADMIN |
| `POST /promo-codes` | 201, промокод | SELLER, ADMIN |

`GET /products`: `page` начинается с 0, `size` по умолчанию 20; фильтры `status` и `category` объединяются через AND. Категория сравнивается точно. Сортировка — `created_at`, затем `id`. Ответ содержит `items`, `totalElements`, `page`, `size`; без фильтра статуса архивные товары также доступны.

Формы запросов, ограничения полей и все ответы описаны в OpenAPI. `/health`, `/docs` и `/openapi.json` доступны без токена. В Swagger UI после получения access-токена через `/auth/login` токен вводится в поле Authorize.

## Бизнес-правила и транзакции

### Товары и заказы

- DELETE товара устанавливает ARCHIVED; повтор не изменяет дату обновления.
- У пользователя может быть не более одного заказа в CREATED или PAYMENT_PENDING. Ограничение дополнительно обеспечено частичным UNIQUE-индексом.
- CREATE_ORDER и UPDATE_ORDER имеют независимые интервалы частоты. Успешная операция фиксируется в `user_operations`; откатившаяся операция не учитывается.
- При CREATE сначала проверяется интервал, затем наличие активного заказа, товары, остатки и промокод. Повторный `product_id` в позициях запрещён.
- Заказ резервирует товар уменьшением `stock`. При UPDATE старый резерв возвращается внутри той же транзакции, затем применяется новый. Позиции, существовавшие непосредственно перед UPDATE, сохраняют `price_at_order`; новые получают текущую цену товара.
- UPDATE разрешён только в CREATED; поле промокода через UPDATE не заменяется. Отмена доступна из CREATED и PAYMENT_PENDING и возвращает остатки и использование промокода. Повторная отмена возвращает 409.
- ADMIN продвигает статус по цепочке CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED. Другие переходы дают 409. Реальной интеграции оплаты нет.

Изменения выполняются в транзакциях: успешный выход фиксирует их, исключение откатывает все изменения. Строки пользователя, заказа, товаров и промокода блокируются в соответствующих операциях через `FOR UPDATE`. Товары блокируются в порядке UUID. Составные чтения используют REPEATABLE READ; транзакции изменения работают с уровнем PostgreSQL по умолчанию READ COMMITTED. Конфликт сериализации или взаимная блокировка преобразуются в 409 `CONCURRENT_MODIFICATION` без автоматического повтора операции.

### Деньги и промокоды

JSON-числа цен и скидок разбираются в Decimal; в PostgreSQL используются NUMERIC(12,2). В HTTP-ответах деньги представлены JSON-числами. Округление скидки — HALF_UP до двух знаков. Сумма до скидки ограничена 9 999 999 999.99.

Промокод должен быть активен, находиться во включительном интервале `valid_from`–`valid_until`, иметь свободную квоту и удовлетворять минимальной сумме. PERCENTAGE до 70 включительно применяется как процент; значение выше 70 означает нулевую скидку. FIXED_AMOUNT ограничен суммой заказа.

При создании заказа использование увеличивается на один. При UPDATE собственное применение не считается чужой занятой квотой. Если новая сумма меньше `min_order_amount`, промокод снимается и использование возвращается. В остальных случаях промокод проверяется заново: истечение срока или деактивация вызывают 422 с откатом UPDATE. Отмена возвращает использование один раз; успешно завершённый заказ продолжает учитываться в квоте.

## Данные

| Таблица | Назначение |
| --- | --- |
| `users` | Уникальный username, хеш пароля, роль |
| `products` | Товар, цена, доступный остаток, статус, продавец и даты |
| `orders` | Владелец, статус, промокод, итог и скидка |
| `order_items` | Позиции, количество и зафиксированная цена |
| `promo_codes` | Код, вид скидки, минимум, срок, квота и число использований |
| `user_operations` | История успешных CREATE_ORDER и UPDATE_ORDER |
| `refresh_tokens` | jti, пользователь, срок и признак отзыва |
| `flyway_schema_history` | История применения миграций |

Миграция создаёт enum-типы, внешние ключи, CHECK-ограничения, уникальность логина, кода и пары заказ/товар. `products_status_idx` индексирует статус товаров; `operations_last_idx` помогает искать последнюю операцию. Даты товаров и заказов устанавливаются defaults, `updated_at` меняется триггером.

## Ошибки и журналирование

Единый JSON-формат:

```json
{
  "error_code": "PRODUCT_NOT_FOUND",
  "message": "Товар не найден",
  "details": {}
}
```

При ошибке валидации `details.fields` содержит поля и причины; при нехватке остатков `details.products` перечисляет товары с requested/available.

| HTTP | Коды |
| --- | --- |
| 400 | `VALIDATION_ERROR` |
| 401 | `TOKEN_INVALID`, `TOKEN_EXPIRED`, `REFRESH_TOKEN_INVALID`, `INVALID_CREDENTIALS` |
| 403 | `ACCESS_DENIED`, `ORDER_OWNERSHIP_VIOLATION` |
| 404 | `PRODUCT_NOT_FOUND`, `ORDER_NOT_FOUND`, `NOT_FOUND` |
| 405 | `METHOD_NOT_ALLOWED` |
| 409 | `PRODUCT_INACTIVE`, `ORDER_HAS_ACTIVE`, `INVALID_STATE_TRANSITION`, `INSUFFICIENT_STOCK`, `USERNAME_TAKEN`, `PROMO_CODE_EXISTS`, `CONCURRENT_MODIFICATION` |
| 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 422 | `PROMO_CODE_INVALID`, `PROMO_CODE_MIN_AMOUNT` |
| 429 | `ORDER_LIMIT_EXCEEDED` |
| 500 | `INTERNAL_ERROR` |

Запросы с телом должны иметь `Content-Type: application/json`. Ошибки Pydantic преобразуются в 400. Аутентификация выполняется до маршрутизации защищённых путей, поэтому отсутствие подходящего токена может дать 401 раньше проверки метода или пути.

Каждый запрос получает UUID в заголовке ответа `X-Request-Id`. Журнал `marketplace.requests` пишет JSON с `request_id`, `method`, `endpoint`, `status_code`, `duration_ms`, `user_id`, `timestamp`. Для POST, PUT и DELETE добавляется тело с рекурсивным маскированием паролей, токенов и секретов по известным именам полей. Тела больше 65 536 байт не включаются в журнал; это ограничение журналирования, а не размера HTTP-запроса.

JWT подписываются HS256. Проверяются issuer `marketplace`, обязательные claims, тип, срок, существование пользователя и совпадение роли. Access действует 20 минут, refresh — 14 дней. Refresh хранится по jti, при обновлении отзывается и заменяется новой парой; повторное использование запрещено. Пароли хешируются BCrypt; максимальная длина — 72 байта UTF-8.

## Настройки

| Переменная | Значение по умолчанию / назначение |
| --- | --- |
| `DATABASE_URL` | Локально `postgresql://market:market@localhost:5432/marketplace`; команды выше явно используют `127.0.0.1`. В контейнере API — хост `db` |
| `JWT_SECRET` | `local-demo-secret-change-me-at-least-32-bytes`; минимум 32 байта UTF-8 |
| `ADMIN_PASSWORD` | `Admin-demo-password-123`; пароль при первоначальном создании `admin` |
| `ORDER_INTERVAL_MINUTES` | `1`; целое неотрицательное число, `0` отключает интервал |
| `TEST_DATABASE_URL` | Обязательна для тестов; отдельная база с суффиксом `_test` |
| `API_URL` | `http://127.0.0.1:8080`; адрес для `scripts/demo.py` |
| `JAVA` | `java`; путь к исполняемому файлу Java для генератора |
| `OPENAPI_GENERATOR_JAR` | `.tools/openapi-generator-cli.jar`; путь к существующему генератору 7.14.0 |

Compose передаёт JWT_SECRET, ADMIN_PASSWORD и ORDER_INTERVAL_MINUTES из окружения; остальные значения соединения заданы в `compose.yml`. Параметр FLYWAY_URL переопределяется в команде тестовой миграции, чтобы она работала с `marketplace_test`.

Демонстрационные пароли и ключ предназначены для локального запуска. Перед внешним размещением требуется настроить собственные значения. Изменение ADMIN_PASSWORD после создания пользователя не меняет уже сохранённый хеш. Приложение не загружает `.env` самостоятельно: для локального процесса значения задаются через CMD `set`.

## Диагностика запуска

| Ошибка | Причина и действие |
| --- | --- |
| Нет пакета `psycopg-binary==3.2.9` | Проверить `.venv\Scripts\python.exe --version`. Для Python 3.14 пересоздать окружение на 3.12 |
| Не найден `requirements-dev.tx` | Имя файла — `requirements-dev.txt`; команда выполняется из корня проекта |
| `$env:...` вызывает ошибку синтаксиса | В CMD переменные задаются через `set "NAME=value"` |
| `'db' is not recognized` | `db` — последний аргумент команды `docker compose up ... db`, а не начало следующей команды |
| Нет `dockerDesktopLinuxEngine` | Docker Desktop не готов или движок не запущен; проверить `docker version` до запуска Compose |
| `ConnectionTimeout` на 5432 | Проверить готовность `db`, доступность опубликованного порта и DATABASE_URL; затем выполнить миграцию |
| `relation "users" does not exist` | В выбранной базе отсутствует миграция Flyway |
| `No module named openapi_server` | Выполнить `scripts\build.py`; для локального API задать PYTHONPATH из раздела запуска |
| Java не найдена | Установить Java 21 или новее и проверить `java -version`, либо задать переменную JAVA |
| `KeyError: TEST_DATABASE_URL` | Задать переменную в том же окне CMD, где запускается pytest |
| Тесты получают 401 при входе admin | В тестовом окне задать ADMIN_PASSWORD из раздела тестов |

Замена окружения Python другой версии без удаления старого:

```cmd
ren .venv .venv-backup
py -3.12 -m venv .venv
.venv\Scripts\python.exe --version
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe scripts\build.py
```

Перед переименованием процессы, использующие старое окружение, должны быть остановлены. Имя `.venv-backup` должно быть свободно; если оно уже существует, выбирается другое имя резервной папки.

При WinError 10048 порт 8080 уже занят. Проверка:

```cmd
curl.exe -i http://127.0.0.1:8080/health
docker compose ps
netstat -ano | findstr :8080
```

Если отвечает ранее запущенный экземпляр этого API, второй запуск не требуется. Для перезапуска локального сервера используется `Ctrl+C` в его окне; для контейнера — `docker compose stop api`. При необходимости локальный API можно запустить на 8081:

```cmd
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8081 --no-access-log
```

В окне проверки и демонстрационного сценария тогда используются:

```cmd
curl.exe -i http://127.0.0.1:8081/health
set "API_URL=http://127.0.0.1:8081"
.venv\Scripts\python.exe scripts\demo.py
```

Проверка PostgreSQL и истории миграций:

```cmd
docker compose ps -a
docker compose logs --tail 100 db
docker compose exec db pg_isready -U market -d marketplace
docker compose exec db psql -U market -d marketplace -c "SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;"
```

## Проверки и ограничения

Зафиксированный результат проверки от 21 октября 2026 года: **20 passed in 159.13s** на Python 3.12.14, HTTP/Uvicorn и PostgreSQL 17.6. Миграция выполнена Flyway OSS 11.7.2. HTTP-сценарий и прямые SELECT подтвердили пересчёт заказа, отмену, возврат остатка и квоты. Повторная генерация дала 36 идентичных Python-файлов; отдельно проверена загрузка генератора. `docker compose config --quiet` прошёл.

Этот результат относится к указанному запуску тестов. Полная сборка образа и запуск всех контейнеров в том прогоне не проверялись из-за недоступного Docker daemon; проверки конфигурации недостаточно для подтверждения контейнерного запуска. Официальные скрытые тесты и нагрузочное тестирование не выполнялись.

Реализованы один API и одна база, без платёжного провайдера, доставки, уведомлений и персонализированной ленты. Статусы оплаты и отправки изменяются административной операцией. В API нет удаления заказов, редактирования промокодов или управления ролями пользователей. Текущие команды предназначены для локального запуска; эксплуатационные настройки резервного копирования, HTTPS и отказоустойчивости не входят в проект.
